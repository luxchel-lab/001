# Интерьерная палитра — как это работает

Блок `#interior` разворачивает базовый цвет клиента в готовую палитру комнаты:
шесть ролей, доли площадей, разбор огрехов, кнопка примерки.

Читать в порядке: [входные данные](#вход-и-состояние) → [роли и характер гаммы](#роли)
→ [сборка палитры](#сборка-палитры-buildinteriorpalettes) → [анализ](#анализ-палитры)
→ [UI](#ui).

## Где что лежит

| Файл | Ответственность |
|---|---|
| `assets/js/podbor.color.js` | цветовая математика: Lab/LCh, ΔE, круг Иттена, `HARMONY_SCHEMES`, `fitToGamut` |
| `assets/js/podbor.data.js` | роли, пресеты характера гаммы, `buildInteriorPalettes`, `ittenAreas`, `paletteChecks` |
| `assets/js/podbor.js` | UI: карточка палитры, ряд «Характер гаммы», сетка сравнения схем |
| `assets/js/podbor.palette.js` | каталог ArchiPaint, 288 оттенков **[генерируется]** |

## Вход и состояние

Палитра строится из четырёх значений глобального состояния `S` в `podbor.js`:

| Поле | Что задаёт | Откуда берётся |
|---|---|---|
| `S.activeHex` | базовый цвет клиента | фото, пипетка, каталог, код RAL, координаты, ссылка |
| `S.mood` | пресет характера гаммы | ряд карточек `#moodGrid`, 12 пресетов в 3 группах |
| `S.scheme` | гармоническая схема | **только** вкладки в «Гармоничных сочетаниях» |
| `S.baseRole` | роль базового цвета | селект `#interiorRole`: `auto` / `main` / `accent` |

Схема выбирается **в одном месте**. Раньше вкладки стояли наверху, а внизу
строились сразу шесть карточек схем — два независимых переключателя одного и
того же. Теперь любая смена идёт через `setScheme(id, opts)`, которая
перерисовывает оба блока и обновляет URL.

## Роли

```js
ROLES = {
  main:        { weight: 60, label: 'Стены' },
  additional:  { weight: 30, label: 'Дополнительный' },  // смежная стена, крупная мебель, шторы
  accent:      { weight: 10, label: 'Акцент' },          // подушки, двери, ниша
  deep_accent: { weight: 10, label: 'Глубокий акцент' }, // столярка, ниши
  ceiling:     { weight: 0,  label: 'Потолок' },
  trim:        { weight: 0,  label: 'Плинтус и столярка' }
}
ROLE_ORDER = ['main', 'additional', 'accent', 'deep_accent', 'ceiling', 'trim']
```

`weight` — приоритет для 60/30/10. Потолок и столярка с нулём: в расчёт долей
площадей они не входят, но в палитре обязательны — без них её нельзя отдать
в работу.

## Характер гаммы: `MOOD_PRESETS`

12 пресетов. В UI ряд называется **«Характер гаммы»**, не «настроение»: пресет
не задаёт настроение, он задаёт целевые светлоты ролей и обработку тона.

Пресеты разложены по трём группам — `MOOD_GROUPS`, поле `group` у каждого
пресета:

| `group` | Заголовок в UI | Чем задан характер | Пресеты |
|---|---|---|---|
| `tone` | Светлота и контраст | перепад LRV между стенами, потолком и столяркой | Светлая база, Высокий контраст, Нюансная гамма, Тёмная база, Белая гамма |
| `temp` | Температура тона | `hueTarget` + `tempPull` тянут все роли к одной трети круга | Тёплая, Холодная, Зелёная гамма |
| `muted` | Приглушённые и нейтрали | `chromaScale` ≤ 0,6 срезает хрому | Припылённая гамма, Бежевая база, Тёплая и Холодная нейтраль |

Группировка — только подача: `buildInteriorPalettes` про `group` ничего не
знает, а `id` пресетов не менялись, потому что уходят в URL (`m=`) и в
сохранённые палитры (`presetId`).

Каждый пресет описывает целевые параметры **по ролям**:

```js
{ id: 'soft_light', title: 'Светлая база', group: 'tone', desc: '…',
  roles: {
    main:        [80, 0.42],   // [целевая светлота L, множитель хромы]
    additional:  [68, 0.55],
    accent:      [46, 1.15],
    deep_accent: [32, 1.30],
    ceiling:     [94, 0.15],
    trim:        [88, 0.25]
  },
  hueTarget: null,    // куда тянуть тон: 62 — охра, 245 — серо-синий, null — не тянуть
  tempPull: 0,        // сила притяжения, 0…1
  chromaScale: 0.8 }  // общий множитель насыщенности пресета
```

Характер гаммы и схема — **две независимые ручки**: пресет меняет светлоты и
насыщенность, схема — углы поворота тона. Ни одна не влияет на другую.

## Сборка палитры: `buildInteriorPalettes`

```js
D.buildInteriorPalettes(baseHex, presetId, {
  baseRoleOverride,  // 'auto' | 'main' | 'accent'
  schemes,           // массив id схем; UI передаёт [S.scheme]
  formula,           // формула ΔE для подбора из каталога
  collections        // ограничить поиск коллекциями
})
```

### 1. Нейтральная база

```js
if (lch.c < 1.5) lch.h = preset.hueTarget == null ? 60 : preset.hueTarget;
```

У чистого серого тон не определён — схемам не от чего отсчитывать углы. Берётся
опора из пресета.

### 2. Роль базового цвета: `autoBaseRole(hex, preset)`

Решает не абстрактная «тёмность», а близость к целевой светлоте роли **в этом
пресете**:

```js
if (lch.c > 48 && mainTarget >= 55) return 'accent';   // очень насыщенный не займёт 60% светлой комнаты
dMain   = |mainTarget - L|
dAccent = |accentTarget - L| × 1.25                    // роли «стены» дана фора
return dAccent < dMain ? 'accent' : 'main'
```

Поэтому почти чёрный оттенок в «Дыхании света» может быть только акцентом, а в
«Ночной роскоши» он и есть стены. `opts.baseRoleOverride` перекрывает автовыбор.

### 3. Распределение ролей по углам схемы

`HARMONY_SCHEMES` задаёт четыре смещения тона:

| Схема | `offsets` |
|---|---|
| Монохромная | `[0, 0, 0, 0]` |
| Аналоговая | `[0, −30, 30, −60]` |
| Комплементарная | `[0, 180, 180, 0]` |
| Раздельно-комплементарная | `[0, 150, 210, 30]` |
| Триада | `[0, 120, 240, 60]` |
| Прямоугольник | `[0, 60, 180, 240]` |
| Квадрат | `[0, 90, 180, 270]` |
| Аналоговая с акцентом | `[0, −35, 35, 180]` |

Порядок ролей зависит от роли базы — базовый цвет всегда получает нулевое
смещение:

```
base = 'main':   [main, additional, accent, deep_accent]
base = 'accent': [accent, main, additional, deep_accent]
```

### 4. Один цвет роли: `buildRoleColor(baseLch, roleId, preset, hueOffset, opts, minL)`

```js
h = pullHue(C.rotateHue(baseLch.h, hueOffset), preset.hueTarget, preset.tempPull)
c = max(0.6, baseLch.c × chromaMul × preset.chromaScale)
L = spec[0]                        // цель пресета, но не ниже minL, если он задан
lab = C.fitToGamut(clamp(L, 6, 97), c, h)
```

Важные детали:

* **углы откладываются по кругу Иттена, а не по тону LCh.** `C.rotateHue`
  переводит тон в художественный круг, поворачивает и возвращает обратно.
  Без этого «комплементарным» к красному выходил бы не зелёный, а голубой:
  в LCh красный и зелёный не лежат на одной прямой.
* **`pullHue(h, target, pull)`** — кратчайший поворот к тёплой или холодной
  части круга, ослабленный на `pull`. Так работают `hueTarget`/`tempPull`.
* **`fitToGamut`** бинарным поиском (24 итерации) снижает хрому, пока цвет не
  войдёт в охват sRGB, сохраняя светлоту и тон.
* **нейтральная база.** При `baseLch.c < NEUTRAL_CHROMA` (6) поворот тона не
  читается и все схемы выглядят одинаково. Неосновным ролям задаётся
  минимальная рабочая хрома `NEUTRAL_CHROMA_FLOOR`:
  `additional: 9, accent: 24, deep_accent: 28`, а `main/ceiling/trim` остаются
  нейтральными. Ровно так и работает дизайнер: спокойный фон плюс цветной акцент.

Дальше цель подбирается из каталога (`nearestOne` → `C.findNearest`), и
возвращается объект с `hex`, `targetHex` (цель до подбора), `lab`, `lch`, `lrv`,
`temperature`, `catalogColorCode/Name/Collection`, `deltaE`.

### 5. Базовый цвет остаётся собой

После сборки четвёрки слот роли `effective` перезаписывается **исходным**
цветом клиента: `hex`, `lab`, `lch`, `lrv`, `temperature`, `isBase = true` и
ближайший каталожный код отдельно. Клиент должен видеть в палитре ровно тот
оттенок, который выбрал.

### 6. Потолок и столярка

Добавляются всегда:

```js
ceiling = buildRoleColor(lch, 'ceiling', preset, 0,          opts, wallSlot.lch.l)
trim    = buildRoleColor(lch, 'trim',    preset, offsets[1], opts)
```

Потолок получает `minL` = светлота стен. Ограничение уходит **в сам поиск по
каталогу** (`findNearest`, параметр `minL`), а не только в цель: иначе цель
поднимали до уровня стен, а ближайший по ΔE цвет всё равно оказывался темнее и
потолок выходил серее стен. Если светлее в каталоге ничего нет, берётся лучшее
из доступного.

Остаточные 138 случаев из 4320 в аудите — все на чистом белом `#FFFFFF` в роли
стен: светлее AP-0101 (LRV 90) в каталоге просто нет. Это предел веера, не расчёта.

### 7. Дедупликация: `dedupeByCode`

Если две роли получили один каталожный код, вторая сдвигается по светлоте
шагами 6…24 с поиском среди 4 ближайших кандидатов.

**Направление выбирается по смыслу роли**, а не «сначала вверх»:

```js
up = preset.roles[col.role][0] >= 50    // светлой роли светлеть, тёмной темнеть
```

Раньше пробовалось вверх, и глубокий акцент всплывал светлее обычного — L44
против L32 при целях 26 и 38. После правки: нарушений порядка светлот 0 вместо
14, максимальный увод от цели 13,9 вместо 20,1.

Слот с `isBase` дедупликация не трогает.

### Возврат

```js
{ baseColor, presetId, presetTitle, presetDesc,
  autoBaseRole, effectiveBaseRole,
  results: [ { schemeId, label, desc, colors: [6 цветов],
               contrast: paletteContrast(colors),
               meta: { presetId, presetTitle, baseRole } } ] }
```

### Асинхронный путь

`buildInteriorPalettesAsync` — то же, но с приоритетом колеровочного API
(`config.apiBase`). Локальный расчёт показывается сразу, ответ API уточняет
результат. Падение API, пустой ответ, отсутствие `apiBase` — всё тихо
возвращается к локальному расчёту. В UI ответ отбрасывается, если за время
запроса сменились цвет, характер гаммы или схема.

## Анализ палитры

### Доли площадей: `ittenAreas(colors)`

60/30/10 с поправкой на **контраст площади Иттена** — седьмой из его семи
контрастов. Иттен взял светлоты чистых тонов по Гёте и потребовал, чтобы площади
были им обратно пропорциональны: жёлтый «кричит» втрое сильнее фиолетового,
значит его нужно втрое меньше.

```js
ITTEN_LIGHT = [6, 7, 8, 8.5, 9, 7.5, 6, 5, 4, 3.5, 3, 4.5]  // по 12 секторам круга
k       = clamp(meanC / 55, 0, 1)        // сила поправки падает вместе с хромой
weights = 1 / ittenLight(hue)
share   = weights[i] / Σweights
raw[i]  = prior × (share / (1/n)) ^ k    // prior = 60, 30, 10
```

Правило выведено для чистых тонов, поэтому на приглушённой палитре `k → 0` и
остаётся обычное 60/30/10. Канонические пары воспроизводятся точно: жёлтый :
фиолетовый = 1 : 3, оранжевый : синий = 1 : 2, красный : зелёный = 1 : 1.

Округление подогнано так, чтобы доли складывались **ровно в 100 %**: остаток
отдаётся самой большой из них. Иначе подпись под полосой показывала 99 или 101.

Возвращает `{ shares: [{role, hex, share}], correction: k, note }`.

### Разбор: `paletteChecks(colors)`

Считает пять измеримых контрастов Иттена и выбирает ведущий:

| id | Оценка |
|---|---|
| `light` | `spreadL / 70` |
| `warm` | `spreadW / 55`, где `warmth = lab.b + lab.a × 0.4` |
| `compl` | близость самой далёкой пары **на круге Иттена** к 180° |
| `sat` | `spreadC / 55` |
| `hue` | `meanC / 75` |

Если лучшая оценка ниже 0,3 — «без выраженного ведущего контраста». Столярка
из выборки исключена: она почти всегда белая и смазывала бы все размахи.

Четыре предупреждения:

1. **спор подтонов** — два приглушённых цвета (`c < 18`) с разницей светлот
   ≤ 12, у которых `undertone` противоположны (`lab.b + lab.a × 0.4`, порог
   нейтральности 2,5);
2. **слипание по LRV** — пары `main↔trim` и `main↔additional` с разницей
   LRV < 5 (`warn` при < 3, иначе `note`). Потолок из этой проверки исключён
   намеренно: белый потолок над почти белыми стенами — норма, а не огрех;
3. **потолок темнее стен** — LRV потолка ниже стен более чем на 3;
4. **акцент не отличим от стен** (`accent-flat`) — ΔE₀₀ между `main` и
   `accent` меньше 6. Срабатывает, когда базовый цвет насильно поставлен в
   роль акцента в почти бесхромной гамме: акцент формально есть, в комнате
   его не видно.

### Контраст: `paletteContrast(colors)`

Размах светлот всей палитры: `> 45` — высокий, `> 24` — средний, иначе мягкий.
Плюс `wallAccentRatio` — отношение контраста по WCAG между стенами и акцентом.

## UI

### Отрисовка

```
renderInteriorSection(scrollIntoView)
├─ нет S.activeHex → показать #interiorEmpty, скрыть #interiorBody
├─ opts = matchOpts({ baseRoleOverride: S.baseRole, schemes: [S.scheme] })
├─ data = D.buildInteriorPalettes(...)  → paint(data)
├─ renderCompare()
└─ есть apiBase → buildInteriorPalettesAsync(...).then(paint)   // с проверкой актуальности
```

`paint(payload)` пишет `S.lastPalettes`, рисует заголовок и **одну** карточку
`buildSchemeCard(payload, payload.results[0], 0, { single: true })`.

`buildSchemeCard` собирает: заголовок «схема · характер гаммы», описание схемы,
полосу долей площадей, шесть строк цветов в порядке `ROLE_ORDER`, блок разбора
(`.scheme-checks`), подвал с контрастом и оценкой, кнопки «Примерить в комнате» /
«Сохранить» / «Скопировать». Флаг `single` добавляет класс `is-single`: карточка
занимает всю ширину, цвета встают в три колонки.

### Сравнение схем

`renderCompare()` по `S.schemeCompare` раскрывает сетку из восьми компактных
карточек (`buildCompareCard`): полоса площадей, шесть образцов, размах светлот.
Клик по карточке зовёт `setScheme(id, { scroll: true })` и сворачивает сетку —
схема меняется сразу в обоих блоках.

> Имя `S.compare` уже занято лотком сравнения отдельных цветов. Состояние сетки
> схем живёт в `S.schemeCompare`.

### Ряд «Характер гаммы»

`renderMoodGrid()` раскладывает `MOOD_GROUPS` и на каждую группу рисует
заголовок (`.mood-group-title` + `.mood-group-hint`) и свою сетку `.mood-grid`.
Карточку собирает отдельная `moodCard(preset)`. Хост `#moodGrid` — теперь
колонка `.mood-groups`, сам он сеткой больше не является.

**Полоска-превью обязана совпадать с палитрой ниже.** `moodCard` считает её
теми же параметрами, что и `renderInteriorSection`:

```js
D.buildInteriorPalettes(S.activeHex, preset.id,
  matchOpts({ baseRoleOverride: S.baseRole, schemes: [S.scheme] }))
```

и сортирует цвета по `D.ROLE_ORDER`, потому что карточка палитры сортирует их
так же. Раньше здесь стояли жёстко зашитая `['analogous']` и сырой порядок
сборки — полоска показывала аналоговую схему независимо от выбранной вкладки,
а при базовом цвете в роли акцента ещё и начиналась с акцента вместо стен.

Отсюда правило: **всё, что меняет палитру, обязано перерисовать и ряд.**
Сейчас это цвет (`archipaint:activecolor`), пресет (клик по карточке), схема
(`setScheme`) и роль базового цвета (`#interiorRole`). Полная перерисовка —
около 13 мс, отдельного кеша ряду не нужно. Полоска-превью каждой строится
`buildInteriorPalettes(S.activeHex, preset.id, { schemes: ['analogous'] })` —
то есть от **текущего** базового цвета, поэтому её нужно пересобирать при
каждой смене цвета. Обработчик `archipaint:activecolor` это делает; раньше не
делал, и ряд оставался от прошлого оттенка, оживая только после клика.

### Что перерисовывается на смену цвета

```js
document.addEventListener('archipaint:activecolor', function () {
  renderResults();          // палитра фото и ближайшие цвета
  renderHarmony();          // круг, объём Lab, четыре цвета схемы
  renderMoodGrid();         // полоски «характера гаммы»
  renderInteriorSection();  // сама палитра
  updateUrlState();
});
```

Полная перерисовка — около 47 мс.

## Результаты аудита

Скрипты проверки гоняют 5760 палитр: 20 баз × 12 пресетов × 3 роли × 8 схем.

| Проверка | Результат |
|---|---|
| базовый цвет входит в палитру без искажения | 4320 / 4320 |
| базовый цвет стоит в заявленной роли | 4320 / 4320 |
| углы схем по кругу Иттена | максимум 4° расхождения — на цвете с хромой 9, где тон съедается округлением до 8 бит |
| порядок светлот ролей | 0 нарушений |
| доли площадей складываются в 100 % | 4320 / 4320 |
| две роли с одним HEX | 0 / 5760 |
| потолок темнее стен | 138 / 4320 — все на чистом белом в роли стен |
| акцент не отличим от стен (ΔE < 6) | 78 / 5760 (1,4 %) — все с базой, вручную поставленной в роль акцента; закрыто предупреждением `accent-flat` |
| столярка не читается на стене (ΔE < 3) | 16 / 5760 (0,3 %) — все «Белая гамма» на почти белой базе; закрыто предупреждением `lrv-trim` |
| палитр хотя бы с одним предупреждением | 24 % |
| ΔE подбора из каталога | средний 3,98 · доля > 5 — 23 % |

Последняя строка — не дефект логики, а плотность веера: 288 оттенков. На
палитре в 1500–2000 средний ΔE в интерьерном диапазоне падает примерно вдвое.

### Не сокращать число пресетов

`audit-presets.js` сравнивает все 66 пар пресетов по среднему ΔE₀₀ между
одноимёнными ролями, на 15 базах:

| | Пара | ΔE | Совпало кодов |
|---|---|---|---|
| ближайшая | Бежевая база ↔ Тёплая нейтраль | 4,8 | 29 % |
| вторая | Светлая база ↔ Бежевая база | 5,3 | 36 % |
| дальняя | Высокий контраст ↔ Тёмная база | 27,8 | 18 % |

Пар с ΔE < 5 — **одна из 66**; пар, где совпадает больше половины кодов
каталога, — **ни одной**. Дублей в наборе нет: любой выброшенный пресет
отнимет реальный диапазон. Лишним был не список, а его плоская подача —
поэтому пресеты сгруппированы, а не сокращены.

## Известная ловушка в `podbor.color.js`

В файле **две** функции с именем `rotateHue`:

```js
// строка 507 — мёртвый код, перекрыт объявлением ниже
function rotateHue(hex, deg) { return adjustLab(hex, 0, 0, deg); }

// строка 895 — эта и работает
function rotateHue(hue, delta) { return ittenToLch(lchToItten(hue) + delta); }
```

Объявления функций поднимаются, побеждает последнее. Ключ `rotateHue` при этом
дважды встречается в объекте экспорта (строки 1087 и 1096) — в ES2015+ это
законно, последний ключ выигрывает, оба указывают на одну и ту же функцию.

Практическое следствие: во второй группе экспорта `rotateHue` стоит рядом с
`lighten/darken/desaturate/mix/adjustLab`, где по сигнатуре ожидается
`(hex, deg) → hex`. Вызов с HEX **не падает**, а тихо возвращает бессмыслицу:

```js
C.rotateHue('#AABBCC', 30)   // → 47.23  (число вместо HEX)
C.rotateHue(60, 180)         // → 241.09 (верно: угол круга Иттена)
```

Живых вызовов с HEX в проекте нет — единственный потребитель
(`podbor.data.js:427`) передаёт угол. Но при доработке легко наступить.
Лечится удалением мёртвой функции и ключа из второй группы экспорта.

# Примерка в комнате — как это работает

Блок `#visualizer` показывает выбранную палитру на фотографии комнаты.
Краска подменяет цвет поверхности, а светотень берётся у снимка.

Читать в порядке: [данные](#данные-сцены) → [подготовка](#подготовка-сцены-prepare)
→ [перекраска](#перекраска-paint) → [интеграция с UI](#интеграция-с-ui).

## Где что лежит

| Файл | Ответственность |
|---|---|
| `assets/js/podbor.photo.js` | движок: разбор сцены и попиксельная перекраска. Ни от чего не зависит, экспортирует `ArchiPaintPhoto` |
| `assets/js/podbor.js` | UI-обвязка: переключатель комнат, `drawRoom`, список поверхностей, раскладка палитры |
| `assets/rooms/<id>.photo.png` | кадр комнаты |
| `assets/rooms/<id>.mask.png` | маска поверхностей к нему |
| `tools/build-room-scene.js` | генератор демонстрационных пластин |
| `tools/png.js` | минимальный кодировщик PNG на `zlib` |

Порядок подключения скриптов: `color → palette → standards → data → photo → podbor`.
`podbor.photo.js` намеренно **не** использует `podbor.color.js`: там функции
возвращают объекты, а на 660 000 пикселей это 660 000 аллокаций на каждую
перерисовку. Матрицы sRGB↔XYZ↔Lab дублированы внутри движка на типизированных
массивах.

## Идея в одной формуле

Для каждого пикселя внутри маски:

```
L_new = L_краски × (L_пикселя / L_опорное)
a_new = a_краски + (a_пикселя − a_среднее) × TEXTURE_KEEP
b_new = b_краски + (b_пикселя − b_среднее) × TEXTURE_KEEP
```

* `L_опорное` — 92-й процентиль светлот **этой поверхности** на исходном кадре,
  то есть её освещённая часть. Среднее увело бы вниз из-за теней, максимум —
  вверх из-за случайного блика.
* `TEXTURE_KEEP = 0.55` оставляет часть собственной пестроты снимка. При нуле
  стена превращается в идеально гладкую заливку и перестаёт выглядеть стеной.

Следствие, которое нужно понимать при поддержке: **на освещённой части
поверхности стоит ровно каталожный цвет** (ΔE 0,2–1,0), а поверхность целиком
в среднем темнее. Это не баг — ради этого примерка и существует.

Из этой же формулы вытекает главное ограничение: светлота **масштабируется**,
а не выдумывается. Тёмная стена на исходном кадре в светлый цвет не
перекрасится. Кадры нужны со светлыми матовыми поверхностями.

## Данные сцены

### Дескриптор

`ArchiPaintPhoto.SCENES` — массив из пяти записей, собранных `map`-ом из
`{id, label}`:

```js
{ id: 'living', label: 'Гостиная',
  photo: 'living.photo.png',
  mask:  'living.mask.png',
  note:  '…' }              // подпись под кадром в UI
```

Добавить комнату = положить два PNG в `assets/rooms/` и дописать `{id, label}`
в начало этого массива. Больше нигде править не нужно.

### Пути к файлам

```js
config = { base: '/assets/rooms/', urls: null }
```

`urlFor(file)` берёт `config.urls[file]`, если задано, иначе `config.base + file`.

* боевая страница Bitrix — `base` по умолчанию, при необходимости
  `podbor({ roomsBase: '/local/templates/main/rooms/' })`;
* `demo/index.html` — `tools/build-demo.js` вписывает `base = '../assets/rooms/'`;
* артефакт — сборщик подменяет всю строку на `config.urls = { 'living.photo.png': 'data:image/png;base64,…', … }`,
  чтобы страница осталась одним файлом без внешних запросов.

### Формат маски

PNG типа 4 — **серый + альфа**:

* **серый канал** — номер поверхности;
* **альфа** — покрытие пикселя этой поверхностью, 0–255.

Альфа нужна для сглаживания краёв: без неё по контуру поверхности идёт зубчатая
лесенка. Генератор считает её суперсэмплингом — доля субпикселей, отданных
победившему номеру.

```js
SURFACE_BY_INDEX = {
  0: null,            // не красится: окно, ковёр, стекло, столешница
  1: 'wall',
  2: 'accentWall',
  3: 'ceiling',
  4: 'trim',
  5: 'furniture',
  6: 'door',
  7: 'floor'
}
```

Ключи совпадают с `key` в `VIZ_SURFACES` (`podbor.js`), поэтому палитра
раскладывается по фотографии тем же кодом, что и по векторной схеме.

## Подготовка сцены: `prepare(photoImg, maskImg)`

Вызывается один раз на комнату, результат кэшируется в `load()`.

Один проход по пикселям кадра:

1. sRGB → линейный через `SRGB_LUT[256]` → XYZ → Lab. Складывается в
   `L`, `A`, `B` (`Float32Array`).
2. `idx[i] = mk[p]` — номер поверхности, `cov[i] = mk[p+3]` — покрытие.
3. Для перекрашиваемых поверхностей копятся `sumA`, `sumB`, `cnt` и
   гистограмма светлот по целым значениям `L` (101 корзина).

Второй проход по 256 возможным номерам считает `refL[s]` (92-й процентиль,
но не ниже 6), `meanA[s]`, `meanB[s]`.

Третий проход по пикселям кладёт в кэш всё, что **не зависит от краски**:

```js
ratio[i] = L[i] / refL[idx[i]]       // во сколько раз пиксель темнее освещённой части
dA[i]    = A[i] - meanA[idx[i]]      // отклонение оттенка от среднего = фактура
dB[i]    = B[i] - meanB[idx[i]]
```

Возвращает:

```js
{ width, height,
  src,          // Uint8ClampedArray — исходные RGBA, нужны для непокрашенных пикселей и краёв
  idx, cov,     // Uint8Array
  ratio, dA, dB,// Float32Array
  out }         // Uint8ClampedArray(n*4) — буфер результата, переиспользуется
```

## Перекраска: `paint(scene, colors, ctx)`

```js
ArchiPaintPhoto.paint(prepared, {
  wall: '#8FA7B3', accentWall: '#7A3B2E', ceiling: '#F2F0EA',
  trim: '#FFFFFF', furniture: '#4E5B4A', door: '#2B2320', floor: '#C99A5B'
}, canvas.getContext('2d'));
```

Сначала целевые Lab раскладываются по номеру поверхности в `tL/tA/tB` и флаг
`on[s]` — один раз на перерисовку, а не на пиксель. Поверхность без цвета в
`colors` остаётся как на исходном кадре.

Затем один проход:

* `on[s] === 0` → копируем исходный пиксель;
* иначе считаем `L/a/b` по формуле выше, Lab → XYZ → линейный RGB;
* линейный → 8 бит через `GAMMA_LUT[4096]` (`linToByte`): `Math.pow` на каждый
  канал каждого пикселя заметно дороже таблицы;
* `cov[i] < 255` → линейно смешиваем результат с исходным пикселем по покрытию.

Результат уходит в `ctx.putImageData`.

**Замеренная стоимость:** кадр 1000×660 — 30–60 мс. Вся тяжёлая математика
(Lab исходника, процентили, отклонения) сделана в `prepare` и переиспользуется.

## Загрузка и кэш: `load(scene)`

```js
var cache = {};   // scene.id → Promise<prepared>
```

`Promise.all` на два изображения, затем `prepare`. При ошибке запись из кэша
удаляется, чтобы следующий вызов мог попробовать снова.

Кадр и маска читаются через `canvas.getImageData`, поэтому **canvas не должен
быть tainted**. По `file://` Chromium помечает его cross-origin и движок падает
с понятным сообщением — локально проверять нужно по HTTP или на data-URI сборке.

## Интеграция с UI

### Состояние

```js
var vizState = {
  wall, accentWall, ceiling, trim, furniture, door, floor,  // HEX
  view: 'living'                                            // id сцены
};
```

`VIZ_SURFACES` связывает поверхность с ролью палитры:

| `key` | Подпись | `role` |
|---|---|---|
| `wall` | Стены | `main` |
| `accentWall` | Акцентная стена | `accent` |
| `ceiling` | Потолок | `ceiling` |
| `trim` | Столярка и плинтус | `trim` |
| `furniture` | Мягкая мебель | `additional` |
| `door` | Дверь | `deep_accent` |
| `floor` | Пол | `null` — в палитру не входит |

У пола `role: null`: краской его не красят, и цвет роли «дополнительный» на
полу раньше ломал всю сцену. В `vizState` он есть и перекрашивается, но
`applyPaletteToVisualizer` его не трогает.

### Отрисовка

```
drawRoom()
├─ photoScene(vizState.view) есть?
│  ├─ да: если canvas ещё не создан — рисуем векторную схему как заглушку,
│  │      затем drawPhotoRoom(stage, scene)
│  └─ нет: photoToken++, drawVectorRoom(stage, roomView(vizState.view))
```

`drawPhotoRoom` инкрементит `photoToken` и запоминает своё значение. После
`await` проверяются два условия: `token === photoToken` и
`vizState.view === scene.id`. Без этого быстрое переключение комнат рисовало бы
кадр, который пользователь уже пролистнул.

При ошибке загрузки показывается **векторная схема той же комнаты** и подпись
в `#vizNote` с текстом ошибки. Схемы (`ROOM_VIEWS`, `ROOM_BUILDERS`) убраны из
переключателя, но живут в коде именно как этот запасной вариант — по одной на
каждую фотосцену.

### Раскладка палитры

`applyPaletteToVisualizer(scheme)` — вызывается кнопкой «Примерить в комнате» в
карточке палитры:

1. по `VIZ_SURFACES` берёт из `scheme.colors` цвет нужной роли (`pickRole`);
2. `drawRoom()` + `renderVizAssign()`;
3. `dispatchToolEvent('archipaint:surfaces', { view })` — калькулятор берёт
   список цветов из этих же поверхностей;
4. прокрутка к блоку и тост.

`renderVizAssign()` строит список поверхностей справа: образец, ближайший
каталожный цвет (`D.nearestOne`) и кнопка «Купить», открывающая карточку краски.

### События

| Событие | Кто бросает | Кто слушает |
|---|---|---|
| `archipaint:activecolor` | `setActiveColor` | палитра фото, гармонии, ряд настроений, интерьерная палитра, калькулятор |
| `archipaint:surfaces` | `applyPaletteToVisualizer` | калькулятор — пересобирает список цветов |

Оба — отменяемые `CustomEvent` на `document`, страница Bitrix может их
перехватить.

## Генератор демонстрационных пластин

`tools/build-room-scene.js` — чистый Node, без зависимостей. Пять комнат
описаны декларативно:

```js
{ id, label, W, H, D, eye, cam,
  win:  { z0, z1, y0, y1 },      // окно на левой стене
  door: { z0, z1, y1 } | null,   // дверь на правой
  floor: 'wood' | 'tile',
  floorAlbedo: [r, g, b],        // необязательно
  rug: { x0, x1, z0, z1 } | null,
  props: [ …prop(box, material) ],
  casters: [ …box ]              // теневые габариты
}
```

Материал предмета задаёт сразу три вещи: номер в маске, базовый цвет пластины и
фактуру. Рендер — трассировка луча из камеры: одноточечная перспектива,
пересечение с плоскостями комнаты и коробками предметов, ближайшее попадание
выигрывает.

Свет — окно как площадной источник плюс **три отскока**: от пола, от
противоположной стены и от потолка. Потолочный обязателен: боковой свет падает
на горизонтальные поверхности почти вскользь, а отскок от пола для них идёт
снизу и по косинусу не считается — без него столы, столешницы и кровать уходят
в тень.

Две ловушки, на которые уже наступили:

* **самозатенение.** Точка на поверхности предмета лежит внутри его же теневой
  коробки. Луч к источнику перекрывался сразу на старте, и мебель не получала
  прямого света вовсе. В `blocked()` коробка, содержащая саму затеняемую точку
  (с допуском `SELF = 3e-3`), пропускается.
* **особенность `1/r²` вблизи источника.** На отдельных сэмплах площадного
  источника знаменатель взрывается и даёт яркие пятна. Смягчается добавкой
  `L.soft` — площади одного сэмпла — к `r²`.

Маска выводится из той же геометрии, поэтому совпадает с кадром пиксель в
пиксель. Запуск: `node tools/build-room-scene.js` или с id одной комнаты.

## Подстановка настоящих кадров

Кода менять не нужно. Нужны два PNG одинакового размера и запись в `SCENES`.

Требования к кадру:

* светлые матовые поверхности там, где будет краска;
* ровный дневной свет, без резкого солнечного пятна;
* без пёстрого декора на стенах;
* 1200–1600 px по ширине — больше только вес и миллисекунды.

Пошаговая выгрузка из Revit (два экспорта одной камеры: кадр + плоские заливки
как готовая маска) описана отдельно — там же таблица цветов фильтров.

## Что стоит знать при доработке

* `prepare` держит семь массивов: `src` и `out` по 4 байта на пиксель,
  `ratio`/`dA`/`dB` по 4, `idx` и `cov` по 1 — итого 22 байта на пиксель,
  около **14 МБ** на кадр 1000×660. Все открытые комнаты остаются в кэше
  `load()`; на пяти комнатах это порядка 70 МБ. Если комнат станет больше,
  кэш стоит ограничить по LRU.
* `refL` и `meanA/meanB` считаются по **всей** поверхности кадра. Если одна
  стена освещена, а другая в глубокой тени, и обе под номером `1`, опорная
  светлота будет компромиссной. Разделять — значит вводить отдельные номера.
* `cov` хранит покрытие только **победившего** номера. На стыке трёх
  поверхностей это приближение; на глаз не видно, но точную альфа-композицию
  оно не даёт.
